# ルナ🌙ガチャ 新カード追加 標準作業テンプレート

> 本書は新カード追加時に、依頼者が渡す情報とCodexが実施する標準手順を定める。
> UI分離、large / mini、管理画面の前提は [UI分離・カード管理設計.md](UI分離・カード管理設計.md) を参照する。
> 本書は手順テンプレートであり、未確定のロゴ、フレーム、UIデザインをCodexが推測して作ることは認めない。

## 1. 適用範囲と原則

- 既存N/Rの完成画像方式と、新規overlay方式は共存させる。
- N01〜N12およびR01〜R12はcompleted-image方式の正式完成カードであり、通常の新カード追加作業でoverlay方式へ移行・再制作しない。
- N05「鏡」のoverlay試作は技術検証であり、既存N05の正式完成画像を置き換えない。
- 新規SRは、SR01「風の音」から素イラスト + overlay UI方式の正式導入候補として扱う。実カードのlarge / miniとiPhone実機表示を検証して方式を確定する。
- 既存の表示責務を変えない。largeは1連・図鑑詳細、miniは10連開示・10連結果・図鑑一覧で使う。
- 新規カードは、既存IDとの重複確認後にのみ追加する。置換の場合は、置換対象ID・旧カードの扱いを明示する。
- `CARD_POOL`、抽選、図鑑、10連、素材パスは、今回の新カードに必要な最小範囲だけを変更する。
- 正式フレーム、正式ロゴ、正式overlay UIが未確定なら、新規デザインを補完しない。必要素材・仕様を報告して停止する。
- commit / pushは、依頼文で明示された場合だけ実行する。

### 入力時の注意

- `frameVariant` と `logoVariant` が未確定なら、Codexは仮の見た目を作らない。
- overlay方式では、large / miniともUIなし素イラストを指定する。完成画像を素材にする場合は`完成画像方式`を指定する。
- large / miniの役割を明記し、画像の向き・実寸の想定と矛盾がないかを確認する。
- 既存カードの置換では、旧カードを抽選候補・CARD_POOLに残すか除去するかを必ず指定する。

## 3. Codexが実施する標準作業手順

### 3.1 作業開始時の保護と読取

1. `AGENTS.md` と `docs/UI分離・カード管理設計.md` を読む。
2. `git status`、branch、worktree、`origin/main` を確認する。
3. 未コミット変更を破棄、reset、checkout、安易なpullで上書きしない。
4. 対象レアリティ、`CARD_POOL`、既存カード表示関数、既存素材構成を必要最小限で確認する。

### 3.2 入力情報と素材の検品

1. 必須項目（ID、レアリティ、タイトル、large、mini、UI方式）を確認する。
2. `CARD_POOL` と既存素材名からID重複を確認する。
3. 指定されたlarge / mini / ロゴ / フレームのファイル存在を確認する。
4. 画像ごとに実寸、縦横比、形式を確認する。
5. largeとminiの取り違え、同一画像の誤指定、破損・ゼロバイトを確認する。
6. 添付原本を正式配置する場合、必要に応じてSHA-256で同一性を確認する。
7. 素材または仕様が未確定の場合は、推測して補完せず不足事項を報告する。

### 3.3 表示方式の分岐

#### 完成画像方式

- `large` と `mini` を既存の`cardImage()`経路で表示する。
- 画像内のロゴ、レアリティ、タイトル、台詞と、外部UIが重複しないことを確認する。
- 既存N/Rと同じ互換経路を優先する。

#### overlay方式

- `presentation.mode = 'overlay'` を設定する。
- `title`、`roman`、`quote`、`message`、`logoVariant`、`frameVariant` は`presentation`内に置く。
- 共通カードレンダラーを再利用する。カード固有のHTML/CSSを増やさない。
- largeは台詞・メッセージを含め、miniは原則として台詞・メッセージを表示しない。
- 正式ロゴは画像原本を使い、CSSで再現しない。
- 正式frameVariantが未実装・未確定なら、推測でフレームを作らない。

### 3.4 CARD_POOLへの安全な反映

1. 新規追加か置換かを依頼内容に照らして確定する。
2. 新規追加時は対象レアリティの候補数を変更前後で記録する。
3. 置換時は、旧カードが抽選候補に残らないことを確認する。
4. レアリティ全体の排出率は変更しない。
5. `currentCards`、抽選関数、10連タップ開示、SKIP、図鑑登録を不必要に変更しない。
6. `large` / `mini` を正しいroleに設定する。10連にlargeを接続しない。

### 3.5 表示経路の確認

次の経路をコード上で確認する。

| 画面 | 期待するrole |
|---|---|
| 1連開示 | large |
| 10連タップ開示 | mini |
| 10連完成結果 | mini |
| 図鑑一覧 | mini |
| 図鑑詳細 | large |

overlay方式では、共通レンダラーが上記すべてでroleに応じた素イラストとUIを出すことを確認する。完成画像方式では既存画像表示を維持する。

### 3.6 静的検査

最低限、以下を実施する。

- JavaScript構文チェック
- `git diff --check`
- 変更ファイル一覧の確認
- CARD_POOL内のID重複確認
- 素材パスの存在確認
- large / miniの参照先確認
- 抽選率に変更がないことの確認
- 対象外の既存カード、10連、図鑑、1連、SKIPへの不要な差分がないことの確認

### 3.7 large / mini確認用プレビュー

1. 本番データを消費しない、対象カードだけの確認導線を用意する。
2. 既存DEV導線を使える場合は、既存の設計を優先する。
3. 既存DEVを使えない場合は、隔離worktreeまたは一時プレビューに限定する。
4. large / miniの両方を同時または明確に切り替えて確認可能にする。
5. プレビューは石、pull count、collection登録、CARD_POOLを変更しない。

### 3.8 iPhone確認完了条件

依頼でiPhone確認が必須の場合、次を満たすまで「作業完了」としない。

- iPhoneからアクセスできるURLまたは再現可能な確認手順を提示する。
- 同一Wi-Fi一時URLを使う場合、PCのWi-Fi IP、ポート、サーバー継続条件を明記する。
- large / miniの両方を確認できる。
- 確認用導線が本番の石、抽選、図鑑登録へ副作用を与えない。
- 実機での最終見た目確認は、ユーザーが実施したか未実施かを明記する。

### 3.9 commit / push

- 明示的に依頼された場合のみ、必要なファイルだけをstage、commit、pushする。
- 明示がない場合は、ローカル確認・報告で停止する。
- 一時プレビュー用スクリプト、添付原本、隔離worktreeの検証ファイルを意図せず本番へ含めない。

## 5. 現行構造に対する注意

- 現行mainではoverlay共通レンダラー、正式frameVariant、`cards-data.js`、`admin.html` は未実装である。
- 新しいoverlayカードを追加する前に、N05試作の採否と正式ロゴ・正式フレーム仕様を確認する。
- 現行のSR/SSR/URはカード画像を持たないフォールバックカードである。新規カード追加が既存候補の置換か追加かは、毎回依頼で明示する。
- この手順書はカード追加の標準化を目的とし、既存の完成画像カードを強制的に移行するものではない。
